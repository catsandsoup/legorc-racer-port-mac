# Product rules: Supersonic RC native port

Read this at the start of every session. It's the standing rule for the
project.

## Rules for the whole project

- **Boot first.** Nothing else matters until the original game reaches its
  title, menus and gameplay on screen, compared against a trusted
  reference: the original `SupersonicRC.exe` (the Shockwave 10 projector)
  running the same `game.dcr` under Wine. `docs/REFERENCE.md` explains how.
  DirPlayer is a second opinion, not the reference.
- **Gameplay stays original by default.** Any change to physics, timing,
  AI, content or progression is a hook: opt-in, off by default, and behind
  a hidden developer page. The 2003 values live in `src/tuning.h`. Don't
  change a default without a side-by-side against the original.
- **No hand edits to generated data.** Everything under the converted data
  folder is generated by `ssrc-import`. Fix the converter or ship a mod.
  Never edit the output.
- **One interface, many doors.** Esc, the controller's Start button and the
  macOS menu bar all reach the same settings model (`build_options()` in
  `src/game.cpp`). Draw it in the game's own art direction (brushed metal
  panels, chrome italic headings, white italic Verdana-style text) sampled
  from the original menus into one token file. Back returns to wherever the
  player came from. Settings write the game's own variables (the `Tuning`
  table, the Director sound channels).
- **No feature without a UI entry point, saved settings and a README
  line.** Environment variables (`SSRC_*`) are only for developers and
  tests. Nothing appears in a menu until it visibly works. No placeholders.
- **Defaults are the best experience:** Metal renderer, sharp scaling,
  native resolution, controller auto-detected with the right button glyphs,
  music on, game speed 100 %, Original lighting.
- **Writable data lives in `~/Library/Application Support/Supersonic RC`**,
  never in the app bundle. Keep a copy of the player's original files
  there.
- **Check licences before borrowing anything.** No copyrighted or
  game-derived bytes in the repo or the download, ever. A release guard
  scans every commit and every built app.

## Proof

- "Done" means a player can find it, use it with a controller and keep the
  setting, shown by fresh screenshots of the real build. A passing test, a
  surviving process or a primitive count is not proof.
- Every milestone ends with:
  - before/after screenshots
  - measured speed: game speed 1.00× means 2.25 simulated seconds per real
    second and 60 logic updates per second
  - a UX critique and a style critique against the original's screens

  Each critique gives a verdict and at most five ranked fixes, with exact
  changes.
- Test hooks exist and must keep working:
  - `SSRC_DATA` sets the data folder
  - a fresh `HOME` gives a fresh user folder
  - auto-import from Downloads
  - `SSRC_TEST*` runs scripted menu input, inputs and screenshots

  See `game/tools/test_driver.gd`.
- The owner plays the real build every few days. Test the downloadable app
  the way a stranger gets it before any release.

## How we work

- One focused session at a time, hands-on, small milestones.
- Commit and push every change with clear messages. Keep `HANDOFF.md`
  current so any session can resume.
- Re-read this file every session. Argue against your own plan: what
  existing thing makes this unnecessary, and what would a player complain
  about first? Don't treat inherited plans or agent reports as true until
  you've seen the result on screen.
- Ask the owner before consequential architecture changes, downloads,
  publishing or anything irreversible.
